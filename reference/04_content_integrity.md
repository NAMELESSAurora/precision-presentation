# 04 · 内容真实性：账本、素材、讲稿

## 三本账（项目根目录）
- **`claims.yaml`：** 屏幕上每一句可以核对的话都登记，字段为 id、text、type（fact / packaging-language / reading / method-note）、source（含位置）、status（verified / handoff-verified / analytic）、slides。内容替换后，旧条目把 `slides: []` 清空并注明退役原因，不要删掉。
- **`sources.md`：** 写清核实日期，以及每个来源**重新打开过没有**。没读全文的，不用直接引文和页码。参考链接只是查证入口，不等于素材授权。
- **`asset-manifest.yaml`：** 每份素材写明 id、用途、来源（原始 URL / 文件 / 帧时间）、本地路径、尺寸、授权状态、屏幕上的标签、替代方案、处理记录。状态用 `in-use / slot-empty / rejected / failed`。

## 屏幕上的标签（图形 + 文字，不只靠颜色）
| 标签 | 图形 | 用在 |
|---|---|---|
| FACT | 实心圆 | 可以核对的事实，后面跟来源编号，例如 `[R04]` |
| READING | 空心圆 | 我们的解读或工作性区分（“Our working distinction — not a quotation”） |
| PACKAGING | 半填方块 | 商业或包装话语（“packaging language, not neutral history”） |
| MADE HERE | 强调色方块 | 为这次演示制作或生成的东西，写明年份，并说明“不是 X 年代的作品” |

## 占位符的生命周期
1. **没有素材时：** 先用明确标注的占位，例如 AI 图标 “MADE HERE · placeholder, AI-generated”，同时在 `asset-manifest.yaml` 里写清需要什么素材。
2. **真实素材到位：** 改 `content.js` 里的槽位，然后同步更新：标签文字、window 标题栏的文件名（自动）、标注位置、`claims.yaml`、讲稿、PDF。
3. **旧占位文件：** 留在 `assets/` 里不删，在 manifest 里标 unused，并写明怎么恢复。

## 真实素材的做法（本项目做过的）
- **自己 demo 的帧：** 从**母版**（ProRes）抽帧，不从压缩过的 MP4 抽。抽出来后和 MP4 对比平均亮度，确认色域没问题（tv/pc range）。
- **商品或出版方的图：** 用出版方页面上的官方产品照（Shopify 店可以读 `<商品URL>.json` 拿到原图地址）。文件名保持官方原名，并显示在窗口标题栏里。标注只写来源页面列出的包装要素；属于推断的识别（例如“扇贝形标题条就是 obi 卡”）写进 claims 的 scope_note。说明文字写“Contemporary reissue packaging (2019), not an original 1980s cover · photo: product page [R05]”。不放价格和库存。
- **logo / 片名字形参考：** 只拿来对照，不放进成片；从 Wikimedia Commons 之类的公开来源取，并记录。
- **视频重封装：** 去掉 tmcd 时间码轨（`-map 0:v:0 -map 0:a:0 -c copy -write_tmcd 0`），再用 md5 确认音视频流和原片逐包一致。

## 第一人称内容
- 只用讲者本人写的或确认过的句子。模板和空位标 `[待确认]`，永远不替讲者编经历、情绪或场景。
- 讲者自己的作品里本来就有的话（例如 demo 献词“In memory of the movies I loved…”），可以引用，但要注明出处，并且允许讲者关掉（`content.js` 里的 text 设为 null）。

## 嵌入一段长 demo 或开场视频
- 动手前先算账：讲话时间 + 媒体时长 + 翻页时间。超过时限就设计短路线（`06_delivery.md`）。
- 演示文稿要服从 demo：页面上的说法（“12 部电影按年份放进各自年代的播放器”）要逐条对照 demo 的工程文件核实，**包括例外**（有两部片被放进了老录像带，这条例外反而成了“选择”的论据）。
- demo 本身的声音、字幕和片尾署名，是 demo 那边 QA 的结果，要在演示文稿的 qa-report 里引用，不能当成演示文稿这边自己测过。

## 讲稿：大纲 → 外部 LLM → 核对
用户常用 Gemini 写讲稿。流程如下：
1. **写 `speech-outline.md`：**
   - **你要补的空位 P1–P7**：只有讲者知道的事，比如怎么看这些电影、真实感受、不想说的就写“跳过”。
   - **全场主线：** 题目原文和核心论点。
   - **时间和字数预算：** 每页的秒数和词数，完整版和短版都要算。
   - **逐页大纲：** 每次 [CLICK] 讲什么要点、可以用的事实和出处、“不能说”的边界、原样保留的过渡句。
   - **给 LLM 的英文提示词：** 只用大纲里的事实；个人内容只用 P1–P7；缺信息时写 `[NEED INFO]`；每页标出字数；顺带写出短版。
   - **核对清单。**
2. **核对拿回来的稿子（docx）：**
   - **读取：** 用 zipfile 解析 `word/document.xml`，按段落和 run 读取；`<w:br/>` 是行内换行。
   - **核对：** 每个事实回到原始来源去查（Pitchfork 页面、论文摘要、demo 工程文件），不要只查自己的大纲。大纲本身也可能写错：这次就有三处错误出自我的备注。
   - **计时：** 按每分钟 140 词，分别算完整版和短版。
   - **点击位置：** 和 `deck.state().slides` 里每页的步数对齐。
3. **本项目里实际查出的错误类型**（下次优先查）：
   - **声音描述错：** 说“底下只有磁带底噪”，实际上那一刻没有底噪，加的是倒带声。
   - **素材类型说错：** 照片上是黑胶 2LP，稿子写成 CD；还说页面上有“结构图”，其实有照片时结构图已经隐藏。
   - **泛化过头：** “每部片都在它年代的播放器里”，其实有例外。
   - **研究变量措辞不准：** 写成 “lockdown worries”，研究测的是 fear of isolation。
   - **位置说错：** 说“完整片单在最后两页”，实际在 demo 自己的片尾字幕里。
   - **缺失：** 没说“不是官方 MV”，也没提歌名。
   - **语法：** “an 1980s” 应为 “a 1980s”。
   - **过度断言：** “can easily overlap”、“many will hear”。
4. **修改：**
   - **原稿不动：** 另存为 `… (revised).docx`，保留原来的段落属性、粗体 [CLICK] 标签、斜体标题和行内换行。
   - **引号风格：** 和原稿保持一致；原稿用直引号，就不要混进弯引号。
   - **核对：** 改完后检查 XML 是否良好，再用 Word COM（`SaveAs2 … 17`）转成 PDF 看一遍。
   - **说明改动：** 告诉用户改了什么、为什么；哪些措辞是你补的（来自用户自己在别处的原话），由用户确认。
   - 讲稿不进提交包；如需放进演讲者窗口，另行询问。
